# results/ analysis reports + results-report skill — design

Date: 2026-07-30
Status: approved in conversation; implementation plan to follow.

## Goal

Stated by the user: opening `results/` and reading the AI-written report should
immediately answer three questions — **what is this result doing, what is the core
conclusion / figure, and which script produced it.**

Two deliverables:

1. **11 reports** — one `README.md` per results directory (10) plus a top-level
   `results/README.md` index.
2. **A `results-report` skill** — the same convention packaged so that every future
   run that produces `results/` data writes its report before the work is delivered.

## Deliverable 1: the reports

### Filename

`README.md`, not `ANALYSIS.md`. GitHub renders `README.md` inline when browsing a
directory, so `results/cz_gate/` shows its report without a second click. That is
exactly the "walk into the folder and immediately know" requirement.

### Template — five sections, in the order the user asked the questions

```markdown
# <dir> — <one-line topic>

## What this is            <- "what is this result doing"
1–2 sentences: which physical question this answers, why it was run.

## Key findings            <- "what is the core conclusion"
Up to 5 bullets — as many as the data actually supports, no padding. Each carries a
concrete number and names the field it came from
(e.g. `validation.json: best_exact_infidelity`).

## Figures                 <- "what is the core figure"
1–3 `![](x.png)` references, one sentence each on what the figure shows.
A leading note: figures are not in git; run the command below to produce them locally.

## Data and provenance     <- "which script produced it"
Generating script/notebook, file-layout table, key parameters.

## Reproduce
Copy-pasteable commands.
```

The two sweep families get **one family-level report each**, with a table row per
spacing sub-store (`a3.0 … a10.0`, plus `legacy_c6-874`) listing grid size, sweep
status, and best point. Not one report per sub-store — 11 near-duplicate documents
would rot.

### Top-level index

`results/README.md`: a 10-row table — directory, one-line topic, generated by,
status — as the single entry point.

### Analysis depth

Read the existing artifacts (json/npz/csv) and extract real numbers; summarise
conclusions already recorded in notebook markdown, `docs/`, and git history.
**No simulation is re-run.** Every number must be traceable to a named field.

### Figures

No **new** figures are added to git. `.gitignore` excludes `*.png` and `*.pdf`, and
the 74 PNGs in `results/` total 102.8 MB (1.4 MB average). Reports reference them by
relative path, note that they are not tracked, and give the command that regenerates
them. A reader with the data (the user) sees the figures; a fresh clone knows how to
produce them.

One pre-existing exception, discovered during the review and worth stating because it
is the right line: `results/297_laser_noise/ECDL_phasenoise.png` and
`seed_lasernoise.png` **are** tracked — gitignore does not apply to already-tracked
files. They are *measured input data* (the digitized source plots), whereas
`psd_model.png` is a *generated* figure and stays untracked. Reports should not
disturb either state.

### Provenance

Every remaining directory has an identified generating script or notebook, so no
report needs an "unconfirmed" provenance section. The two directories that had none —
`effective_theory` (a single markdown note) and `lattice_dynamics` (benchmarks whose
producing notebook `scripts/notebooks/run_quench_benchmark.ipynb` no longer exists) —
were deleted on the user's decision, 2026-07-30. Script names are still never
invented: if a future directory has no identifiable producer, its report says so.

## Deliverable 2: the results-report skill

### Location

`.agents/skills/results-report/SKILL.md` — project scope, committed with the repo.
The convention is repo-specific (this `results/` layout, these script conventions,
the figures-not-in-git rule), so a user-global skill would leak into other projects.

### Contents

- A `description` whose trigger is explicit: **after any script or notebook run that
  creates a new `results/` directory or new data in one, and before delivering to the
  user.**
- The five-section template above.
- Hard rules: every number traceable to a named field; unconfirmed provenance is
  written as "unconfirmed" and script names are never invented; figures use relative
  paths and carry the not-in-git note.
- A pre-delivery checklist matching the verification criteria below.
- A rule to add a row to `results/README.md` whenever a new results directory
  appears, so the index does not rot.

### Validator

`.agents/skills/results-report/validate.py` — checks that a report has all five
sections, that every `![](…)` path exists on disk, and that every script/notebook
path named in the Reproduce section exists. The 13 reports need these checks anyway;
packaging them makes the check reusable.

### Enforcement

The skill alone is advisory — the model has to decide it applies. So `AGENTS.md`
gains one clause under `## Agent skills`: any run that produces new `results/` data
must complete that directory's README before the work is delivered. `AGENTS.md`
enters context every session and outranks skills, which is the cheapest reliable
enforcement. No hook: a `PostToolUse` hook cannot tell reliably which run actually
produced new data, and false positives would be noisy.

## Review findings each report must state

Turned up by the 2026-07-30 directory-by-directory review; these are defects a report
would otherwise paper over.

- **`zxz_direct_qoc`** — the 40 `direct_pulse{1,2}_seed*.npz` carry **three different
  key sets**: 29 have `fidelity_rollout` + `warm_started`, 3 have only
  `fidelity_rollout`, 8 (all of pulse2) have neither. The two fields were added by
  `7d61c48` and `14295d6`, so 11 of 40 artifacts predate the current script.

  **Resolved 2026-07-31 — no re-run, no artifact rewrite.** `fidelity_rollout` is a
  pure function of the stored `u_omega`/`u_delta`, so it was recomputed for pulse2
  with the script's own model and propagation. The method was first validated against
  the 32 pulse1 artifacts that do store it: worst deviation **0.000e+00**, bit
  identical. For pulse2 the rollout fidelity matches the recorded variational
  `fidelity` to **≤1.3e-10** with the seed ranking unchanged (best is seed 4,
  F = 0.99219 either way). So the pulse2 arm is validated, not merely unvalidated-
  looking. The artifacts are deliberately left byte-for-byte as the study wrote them:
  every consumer already falls back (`cmd_validate` line 469, `cmd_plot` line 506, the
  warm-start guard lines 164-166), and the only unconditional use is on rows freshly
  computed within a run. The report states the schema difference and this measurement
  rather than implying the data is suspect.

  Also: nothing in this directory is git-tracked (0/53).
- **`cz_gate/error_characterization/`** — no code references it, and its six
  `mc_*.txt` self-report "MonteCarloResult saved 2026-02-11/12", i.e. before the
  2026-07-15 `src/ryd_gate` rewrite; they were committed on the rewrite day by
  `eebce3e`. The report flags them as pre-rewrite and does not restate their numbers
  as current.
- **`max_leakage_ode`** — `a3.0/reports/pilot.json` has 9 keys where a4.0/a5.0/a7.0/
  a10.0 have 8 (the deleted-from-git `legacy_c6-874` also had 9), so a3.0 is
  same-generation as legacy and the other four were run later. The `legacy_c6-874`
  store remains on disk but is untracked as of 2026-07-30.
- **`anneal_sweep`** — both generating scripts were committed 2026-07-24, two days
  after the newest data (2026-07-22). The report notes the gap rather than implying
  the data is a current-script product.
- **`cz_gate`** (nb01, committed 2026-07-20 vs data 2026-07-18) and **`cz_grape_e2e`**
  (script 2026-07-24 vs data 2026-07-23) have the same kind of gap; note it, do not
  dramatize it.
- **`max_leakage_297`** — `a3.0` was being rewritten by a concurrent session during
  the review, so any file counts must be re-measured when its report is written.

## Verification criteria

1. 13 reports exist; each has all five sections.
2. Every `![](…)` path in every report exists on disk.
3. Every script/notebook path in every Reproduce section exists.
4. Every quoted number is traceable to a named field or file (json/npz key, csv
   column, log line) — not to prose.
5. Anything unverifiable is written as "unconfirmed" — zero fabrication.
6. `validate.py` passes on all 13 reports.

## Out of scope

- Changing `.gitignore` or committing/re-exporting figures.
- Re-running any simulation, refitting, or producing new figures.
- Reorganising `results/` itself.
- Backfilling the three unconfirmed provenances by guessing.

# results/ analysis reports + results-report skill — design

Date: 2026-07-30
Status: approved in conversation; implementation plan to follow.

## Goal

Stated by the user: opening `results/` and reading the AI-written report should
immediately answer three questions — **what is this result doing, what is the core
conclusion / figure, and which script produced it.**

Two deliverables:

1. **13 reports** — one `README.md` per results directory (12) plus a top-level
   `results/README.md` index.
2. **A `results-report` skill** — the same convention packaged so that every future
   run that produces `results/` data writes its report before the work is delivered.

## Deliverable 1: the reports

### Filename

`README.md`, not `ANALYSIS.md`. GitHub renders `README.md` inline when browsing a
directory, so `results/cz_gate/` shows its report without a second click. That is
exactly the "walk into the folder and immediately know" requirement.

### Template — five sections, in the order the user asked the questions

```markdown
# <dir> — <one-line topic>

## What this is            <- "what is this result doing"
1–2 sentences: which physical question this answers, why it was run.

## Key findings            <- "what is the core conclusion"
Up to 5 bullets — as many as the data actually supports, no padding. Each carries a
concrete number and names the field it came from
(e.g. `validation.json: best_exact_infidelity`).

## Figures                 <- "what is the core figure"
1–3 `![](x.png)` references, one sentence each on what the figure shows.
A leading note: figures are not in git; run the command below to produce them locally.

## Data and provenance     <- "which script produced it"
Generating script/notebook, file-layout table, key parameters.

## Reproduce
Copy-pasteable commands.
```

The two sweep families get **one family-level report each**, with a table row per
spacing sub-store (`a3.0 … a10.0`, plus `legacy_c6-874`) listing grid size, sweep
status, and best point. Not one report per sub-store — 11 near-duplicate documents
would rot.

The existing `results/effective_theory/find_phase_perturbation_check.md` stays as
is; that directory's README links to it as a verification record.

### Top-level index

`results/README.md`: a 12-row table — directory, one-line topic, generated by,
status — as the single entry point.

### Analysis depth

Read the existing artifacts (json/npz/csv) and extract real numbers; summarise
conclusions already recorded in notebook markdown, `docs/`, and git history.
**No simulation is re-run.** Every number must be traceable to a named field.

### Figures

Figures are **not** added to git. `.gitignore` excludes `*.png` and `*.pdf`, and the
74 PNGs in `results/` total 102.8 MB (1.4 MB average). Reports reference them by
relative path, note that they are not tracked, and give the command that regenerates
them. A reader with the data (the user) sees the figures; a fresh clone knows how to
produce them.

### Unconfirmed provenance

`297_laser_noise`, `effective_theory`, and `lattice_dynamics` have no referencing
code anywhere in the repo. Their reports write **"unconfirmed"** in the provenance
section and list only the evidence derivable from the data itself. Script names are
never invented. These three need the user's confirmation afterwards.

## Deliverable 2: the results-report skill

### Location

`.claude/skills/results-report/SKILL.md` — project scope, committed with the repo.
The convention is repo-specific (this `results/` layout, these script conventions,
the figures-not-in-git rule), so a user-global skill would leak into other projects.

### Contents

- A `description` whose trigger is explicit: **after any script or notebook run that
  creates a new `results/` directory or new data in one, and before delivering to the
  user.**
- The five-section template above.
- Hard rules: every number traceable to a named field; unconfirmed provenance is
  written as "unconfirmed" and script names are never invented; figures use relative
  paths and carry the not-in-git note.
- A pre-delivery checklist matching the verification criteria below.
- A rule to add a row to `results/README.md` whenever a new results directory
  appears, so the index does not rot.

### Validator

`.claude/skills/results-report/validate.py` — checks that a report has all five
sections, that every `![](…)` path exists on disk, and that every script/notebook
path named in the Reproduce section exists. The 13 reports need these checks anyway;
packaging them makes the check reusable.

### Enforcement

The skill alone is advisory — the model has to decide it applies. So `CLAUDE.md`
gains one clause under `## Agent skills`: any run that produces new `results/` data
must complete that directory's README before the work is delivered. `CLAUDE.md`
enters context every session and outranks skills, which is the cheapest reliable
enforcement. No hook: a `PostToolUse` hook cannot tell reliably which run actually
produced new data, and false positives would be noisy.

## Verification criteria

1. 13 reports exist; each has all five sections.
2. Every `![](…)` path in every report exists on disk.
3. Every script/notebook path in every Reproduce section exists.
4. Every quoted number is traceable to a named field or file (json/npz key, csv
   column, log line) — not to prose.
5. Anything unverifiable is written as "unconfirmed" — zero fabrication.
6. `validate.py` passes on all 13 reports.

## Out of scope

- Changing `.gitignore` or committing/re-exporting figures.
- Re-running any simulation, refitting, or producing new figures.
- Reorganising `results/` itself.
- Backfilling the three unconfirmed provenances by guessing.
